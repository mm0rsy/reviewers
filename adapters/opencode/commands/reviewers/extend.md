# Extend — add a new domain reviewer with the user

Help the user extend their review setup with a reviewer for a domain/technology the plugin
does not ship a template for (e.g. CAPL, Go, Rust, VHDL, Terraform modules, a proprietary
DSL) — or deepen an existing reviewer. Reference documents:
- `.opencode/skills/review-orchestration/references/review-schema.md` — the format the result must satisfy
- `.opencode/skills/review-orchestration/references/templates/_custom.md` — the annotated meta-template (minimal reference)
- `.opencode/skills/review-orchestration/references/templates/` — built-in domains, useful as structural relatives

Arguments given by the user: `$ARGUMENTS` (the domain/technology, plus any hints).
- If no domain was given, ask what technology or concern the reviewer should cover.
- `--auto` → skip the interview: apply your best-judgment draft end-to-end and finish with
  a clearly marked list of every assumption made. Also behave as if `--auto` were set
  whenever no user answer can arrive (one-shot/non-interactive execution) — never end an
  unattended run with an unanswered question and nothing written.

## Step 1 — Understand the target domain
- If review.md already has a reviewer covering this domain, switch to **deepen mode**:
  propose sharper focus areas, missing globs, or a guideline doc for it (steps 3–5 apply
  the same way, editing the existing section instead of adding one).
- Identify the closest built-in template as a structural relative (e.g. CAPL → embedded +
  testing; Go/Rust → backend) — inherit its shape, not its content.

## Step 2 — Find the domain's footprint in this repo
Detect where the technology lives: file extensions and directories (e.g. `*.can`, `*.cin`
for CAPL; `*.go`, `go.mod`; `*.rs`, `Cargo.toml`), plus existing tooling that encodes team
rules already (linters, formatters, CI jobs). Verify every glob you will propose actually
matches at least one file — a reviewer with dead globs never activates. If the technology
is not in the repo yet (preparing for future code), say so and proceed with standard globs.

## Step 3 — Build the reviewer section WITH the user
Fill the meta-template deliberately:
- **files**: the verified globs from step 2.
- **focus**: 4–7 areas ordered by priority, specific to the technology's real failure modes
  (for CAPL: e.g. event-handler timing, CAN signal validity checks, testcase verdict
  hygiene; for Go: goroutine/context leaks, error wrapping; for Rust: unsafe blocks,
  unwrap/expect discipline, lifetime-driven API design). Draft from your domain knowledge,
  then let the user reorder/edit.
- **optional keys**: propose `always`, `severity-floor`, or `depth` only when the domain
  warrants it, and say why.
- **prose lore**: ask for constraints the keys can't express (target hardware, protocol
  versions, legacy zones).
Interview in ONE round if possible: present a complete draft and ask for corrections,
rather than twenty questions. With `--auto` (or unattended), skip the round entirely and
apply the draft.

## Step 4 — Draft the guideline document (recommended)
Unless the team already has one, draft `docs/<domain-slug>-guidelines.md` as a **starter**:
naming conventions, forbidden constructs, required patterns, tooling expectations — from
your knowledge of the technology's community standards, marked at the top as
"Starter guidelines generated by /reviewers:extend — refine as a team." Link it from the
reviewer's `guidelines:` key. If the team has existing docs, link those instead.

## Step 5 — Wire in and validate
1. Append the new section to review.md (or update the existing one in deepen mode),
   preserving the file's formatting.
2. Dry-run: re-parse review.md per the schema and confirm the new section parses clean;
   run the globs against the repo and show what currently matches.
3. Show the final section and guideline doc to the user.
4. Remind them: commit review.md and the guideline doc — that's how the extension reaches
   every teammate on every platform; no plugin change is ever needed. The section and the
   guideline doc are theirs to extend further at any time, and `/reviewers:extend <domain>`
   can be re-run later to deepen it.
